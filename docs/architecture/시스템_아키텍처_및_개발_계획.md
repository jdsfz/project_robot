# project_robot — 시스템 아키텍처 및 개발 계획

문서 버전 0.1 · 3인 팀 · 요구명세서 v0.1 기반 초안  
진행 상황 갱신: 2026-11-14

## 1. 문서 목적과 현재 상태

이 문서는 산업안전 보호장구 전달 자율주행 로봇의 요구사항을 시스템 구성, 개발 순서, 인터페이스와 시험 계획으로 정리합니다. 역할 분담은 아직 담당자를 배정하지 않은 상태에서 작성한 검토안이며, 일정과 정량 기준도 미확정입니다.

요구사항 원본은 산업안전_자율주행_요구명세서.docx입니다. 요구사항별 상태와 완료 판정은 원본 명세서의 규칙을 따릅니다. 이 문서는 구현 완료를 선언하는 자료가 아닙니다.

현재 확인된 진행 상태:

- 팀원 전원이 Ubuntu 24.04 / ROS 2 Jazzy / Gazebo Harmonic 설치를 완료했습니다(사용자 확인).
- 보유 장비는 [Raspbot V2](https://www.icbanq.com/P016515116)와 [Raspberry Pi 5 버전 IoT 키트](https://www.icbanq.com/P013149476)입니다(사용자 확인).
- Raspberry Pi에 연결한 실물 라즈봇 수동 조작이 동작합니다(사용자 확인). examples/manual/manual_jiy.py는 수동모드 시험용 파일이며 Flask 웹 UI에서 Raspbot_Lib로 바퀴·카메라 서보를 제어합니다. 정식 ROS 제어 노드나 Gazebo 연동 구현은 아닙니다. 현재 바퀴 명령은 전진·후진·제자리 좌우회전·정지이고, 명령 갱신이 0.5초 이상 끊기면 정지합니다. Pi의 OS·ROS 배포판과 Gazebo 연결 방식은 아직 미확인입니다.
- 저장소에는 robot_teleop ROS 2 Python 패키지 골격, /cmd_vel과 map·odom·base_link 인터페이스 초안, 수동 조작 시뮬레이션 및 참고 예제가 있습니다.
- Gazebo에서 라즈봇을 작동시키는 모델·메카넘 구동 구성은 추가 작업이 필요합니다. Nav2 자율주행, CCTV 인식, 임무 관리, 운영 UI, 전달·복귀는 구현 완료로 간주하지 않습니다.
- 1차 시연 범위와 안전 정지 기준은 미팅 전까지 미정입니다.

## 2. 목표와 1차 범위

목표는 CCTV에서 보호장구 미착용 의심 대상을 확인하고, 안전한 전달 위치를 정한 뒤 로봇이 보호장구를 전달하고 수령을 확인해 대기 지점으로 복귀하는 흐름을 단계적으로 검증하는 것입니다.

요구명세서 v0.1의 제안 범위는 단일 층, 로봇 1대, 사용자 직접 수령입니다. 다음 항목은 팀이 확정하기 전까지 미정으로 유지합니다.

- 이동 대상 연속 추적의 1차 포함 여부
- 자동 도킹·충전의 1차 포함 여부
- 자동 출동과 운영자 승인 경계
- 속도, 정지거리, 사람·벽 간격, 좌표 오차, 영상 성능 등 측정 기준
- 실제 로봇·카메라·센서·모터 드라이버의 모델과 인터페이스

1차 범위 초안에서는 위험구역 안으로 진입하지 않고 계단·낙하 구역 접근을 제한합니다. 실제 산업 현장 적용은 교육용 시연 개발과 분리된 검증·승인 과제입니다.

## 3. 시스템 구성안

아래는 요구명세서에서 도출한 논리 구성입니다. ROS 패키지와 토픽 연결은 인터페이스 합의 후 확정해야 합니다.

    CCTV / 카메라
        ↓
    영상 입력 및 사람·보호장구 감지
        ↓
    대상 상태와 추적 유효성 ───── 운영자 화면
        ↓                              ↕
    임무 관리자 ←──────────────→ 임무·오류·모드 표시
        ↓
    ROS 2 위치 추정·지도·경로 계획 ← 거리 센서·오도메트리
        ↓
    안전 제어: 정지 우선·명령 만료·모드 중재
        ↓
    모터 제어부 및 구동 베이스
        ↕
    로봇 위치·주행 상태
        ↓
    임무 기록·로그·시험 증거

임무 관리자는 전달 위치와 출동 조건을 검토하고, 보호장구 적재·수령 확인을 포함한 임무 상태를 관리합니다. 카메라 대상 좌표와 로봇 지도 좌표를 연결하는 방법은 실제 카메라 배치와 보정 절차가 확인된 뒤 정해야 합니다.

### 책임 경계 초안

- 영상 인식은 사람·보호장구 상태와 관측 유효성을 출력합니다. 판정 불가를 미착용으로 처리하지 않습니다.
- 임무 관리자는 대상·위치·적재·센서·배터리 등의 출동 조건과 임무 상태를 관리합니다.
- 주행 구성은 위치 추정, 경로 생성·재탐색, 장애물 정보를 사용해 목표를 수행합니다.
- 안전 제어는 정지 우선, 명령 만료, 모드 배타, 센서·통신 장애 시 정지 조건을 집행합니다. 하드웨어 독립 정지는 별도 장치와 시험으로 확인해야 합니다.
- 운영 화면과 기록은 모드·임무·오류를 표시하고, 임무 확인·취소·수동 조작과 시험 이력 확인을 지원합니다.
- 전달 기능은 적재, 안전한 전달 위치와 수령 완료를 확인합니다. 수령과 착용 완료는 서로 다른 상태입니다.

## 4. ROS 인터페이스 방향

현재 저장소의 [ROS 인터페이스 초안](../interfaces/ros_interfaces.md)은 /cmd_vel (geometry_msgs/msg/Twist)과 좌표 프레임 이름만 다룹니다. 아래는 추가 합의가 필요한 범주이며, 토픽 이름·메시지 형식·QoS는 확정되지 않았습니다.

| 인터페이스 범주 | 전달할 정보 | 확인할 점 |
|---|---|---|
| 구동 명령 | 속도 또는 주행 목표 | 명령 만료, 정지 우선, 허용 속도 |
| 위치·상태 | 위치, 방향, 위치 유효성, 센서 상태 | 좌표계·단위·시각·유효성 기준 |
| 장애물·지도 | 고정/임시 장애물, 금지구역 | 갱신·제거 조건, 미검증 구조물 제한 |
| 대상 관측 | 임시 추적 ID, PPE 판정, 신뢰도, 촬영 시각, 좌표 | 판정 불가, 추적 단절, 좌표 변환 오차 |
| 임무 관리 | 임무 ID, 상태, 전환 사유, 취소·결과 | 중복·만료 명령 방지, 동시 요청 |
| 운영·오류 | 모드, 오류 코드, 정지 이유, 복구 조건 | 복구만으로 자동 재개 금지 |
| 전달·전원 | 적재, 수령, 배터리, 충전 확인 | 도착과 충전 상태 분리 |

제어 명령과 상태 메시지에는 임무/명령 식별자와 유효 시각을 포함하는 방안을 검토합니다. 구체적인 ROS 메시지와 수치 기준은 팀 합의 후 인터페이스 문서와 구현에 함께 반영합니다.

## 5. 세 명 역할 분담 제안

프로젝트 업무는 세 파트로 나눠져 있고, 사람별 담당자는 아직 배정하지 않았습니다. 아래 제안은 기능 소유권과 협업 경계를 구체화한 초안입니다. 담당자 배정 전 팀원의 경험·장비 접근성·가용 시간을 보고 업무량을 조정합니다. 1차 범위 미정 항목은 확정된 구현 약속이 아닙니다.

### A. 로봇 기반·주행

**목표:** Gazebo와 실물 라즈봇에서 공통으로 사용할 수 있는 구동 기반을 만들고, 승인된 범위의 이동·정지·장애물 대응을 담당합니다.

- 시작 작업: Raspberry Pi의 OS·ROS 배포판, Raspbot_Lib, 모터 보드와 센서 연결을 조사합니다. 수동모드 시험 파일 examples/manual/manual_jiy.py의 입력과 모터 출력 경로를 기록합니다.
- 시뮬레이션: 실물 차체와 메카넘 휠 배치를 반영한 URDF/Xacro 및 Gazebo 모델을 구성합니다. 휠 반경·간격·회전 방향·센서 프레임을 실제 측정 또는 제조사 자료로 확인합니다.
- 제어: Gazebo에서 전후진·제자리 회전·정지를 먼저 재현하고, 1차 범위가 합의되면 횡이동·주행 목표·Nav2 등으로 확장합니다. 실물 하드웨어 출력과 Gazebo 출력을 구분된 어댑터로 두고 공통 제어 규약을 맞춥니다.
- 주행 기반: 범위에 포함될 경우 odometry·TF·센서 입력, 위치 추정, 지도, 경로 계획, 장애물 대응과 재탐색을 구성합니다.
- 검증: 방향·속도 대응, 정지 명령, 명령 만료, 센서 단절 및 시뮬레이션/실물 차이를 기록합니다. 안전 정지의 하드웨어 독립성은 팀 공동 검토로 확인합니다.

**주요 산출물:** 로봇 모델과 Gazebo 월드, bringup/teleop 구성, 구동·센서 인터페이스 설명, 실물·시뮬레이션 비교 시험 기록.

**담당 요구사항 예시:** ENV, MAN, NAV, OBS, NFR-01·02·04·05, SAF 중 이동·정지 관련 항목.

### B. 영상 인식·대상 위치

**목표:** 카메라 관측에서 사람과 보호장구 상태를 판단하고, 그 결과가 임무 판단에 안전하게 사용될 수 있도록 유효성과 위치 정보를 제공합니다.

- 입력: CCTV 또는 시험용 카메라 영상의 출처·시각·해상도·끊김 상태를 전달합니다. 실제 카메라가 준비되기 전에는 사용할 수 있는 저장 영상과 Gazebo 카메라를 구분합니다.
- 인식: 사람별 안전모·조끼·목장갑 상태를 착용·미착용·판정 불가로 구분합니다. 불확실하거나 가려진 경우 판정 불가를 보존합니다.
- 추적: 임시 추적 ID, 연속 관측 여부, 신뢰도와 마지막 관측 시각을 관리합니다. 추적이 끊기거나 ID가 바뀌면 같은 사람이라고 단정하지 않습니다.
- 좌표: 카메라 좌표와 지도 좌표의 변환·보정 방법을 정하고, 위치 오차와 관측 유효시간을 기록합니다. 전달 목표를 직접 확정할지, 후보 위치를 임무 파트에 전달할지는 인터페이스 합의로 정합니다.
- 검증: 사람별 장구 연결 오류, 종류별 정밀도·재현율, 판정 불가 비율, 가림·저해상도·조명 변화, 추적 단절과 좌표 오차를 평가합니다.

**주요 산출물:** 영상 입력 구성, PPE 판정·추적 모듈, 관측/대상 메시지 정의, 보정 설정, 평가자료와 성능·실패 사례 기록.

**담당 요구사항 예시:** VIS, NFR-03, DAT-02·05, SAF-04 일부.

### C. 임무·운영·통합

**목표:** 인식 결과와 로봇 이동 기능을 안전한 임무 흐름으로 연결하고, 운영자가 상태·결과·오류를 확인할 수 있게 합니다.

- 임무 상태: 대기·출동 준비·이동·정지/재탐색·수령 대기·복귀·오류 정지 등 상태와 상태 전이 조건을 구현합니다.
- 출동 결정: 인식 유효성, 좌표 유효성, 전달 가능 위치, 적재·센서·배터리 상태를 확인합니다. 자동 출동인지 운영자 승인인지 팀 결정 전에는 정책을 확정하지 않습니다.
- 전달 흐름: 도착과 수령 확인을 구분하고, 수령·미수령·취소·실패 결과를 기록합니다. 착용 완료와 수령 완료도 별도 상태로 관리합니다.
- 운영·기록: 모드, 대상/임무, 로봇 위치, 이동 상태, 오류와 전환 사유를 표시하고 임무 확인·취소 기능을 연결합니다. 임무 ID로 감지부터 종료까지 로그를 추적할 수 있게 합니다.
- 통합: 세 파트 인터페이스와 실행 순서를 조율하고, 재현 가능한 launch/설정 및 통합 시나리오를 관리합니다. 통합시험 취합을 맡더라도 각 파트 담당자가 자기 기능의 시험 증거를 작성합니다.

**주요 산출물:** 임무 상태 설계, 운영 화면/상태 표시, 임무 기록 형식, 통합 실행 구성, end-to-end 시험표와 운용·복구 안내.

**담당 요구사항 예시:** DEL, OPS, DAT-01·03·04, QA, SAF 중 임무 전이·재개 통제 관련 항목.

### 세 파트 사이의 협업 계약

| 연결 | 보내는 쪽 | 받는 쪽 | 초기에 합의할 정보 |
|---|---|---|---|
| 대상 관측 → 임무 판단 | B | C | 임시 대상 ID, PPE 상태, 신뢰도, 촬영 시각, 좌표, 유효/판정 불가 상태 |
| 이동 목표 → 로봇 실행 | C | A | 목표 위치, 좌표계, 임무 ID, 취소·만료 조건 |
| 로봇 결과 → 임무 상태 | A | C | 주행 상태, 위치 유효성, 성공·실패·취소, 오류와 정지 사유 |
| 운영 상태 → 사용자 | C | 운영자 | 현재 모드, 임무 단계, 승인/취소 요청, 오류·복구 필요 상태 |

이 표는 논의 시작을 위한 계약 초안입니다. 토픽 이름·메시지 타입·서비스/액션 구분·QoS·시간 기준은 팀이 결정 기록에 합의한 뒤 ROS 인터페이스 문서에 확정합니다.

### 공동 책임과 업무량 조정

- 각 파트 담당자는 본인 기능의 설계, 구현, 단위·기능 시험과 증거 기록을 맡습니다. C 한 명에게 모든 시험과 문서가 몰리지 않게 합니다.
- 세 명 모두 초기 장비 조사, 인터페이스 합의, 안전 요구 검토와 최종 통합 검토에 참여합니다.
- A 파트에 시뮬레이터와 실물 드라이버 작업이 몰리면 초기에는 Gazebo 기본 구동과 실물 하드웨어 조사로 범위를 나누고, 위치 추정·Nav2는 1차 범위에 따라 후순위로 둡니다.
- B 파트는 데이터 준비와 라벨링에 시간이 많이 들 수 있으므로, 대상 PPE 종류와 평가자료 범위를 먼저 고정합니다.
- C 파트는 UI 구현보다 상태 전이·오류 처리·통합 연결을 우선합니다. UI의 세부 시각화는 일정과 인력 여유에 따라 조정합니다.
- 안전 관련 완료 판정은 구현 담당자 혼자 내리지 않고 다른 두 파트가 시험 결과를 함께 검토합니다.

## 6. 개발 및 검증 단계

기간은 아직 정하지 않았습니다. 단계별 진입 조건과 시험 증거를 확인한 뒤 진행합니다.

| 단계 | 작업 | 완료 증거 예시 |
|---|---|---|
| 0. 장비·환경 기준선 | 실물 장비 목록, Pi의 OS/ROS, 수동조작 코드·명령 흐름, 치수·센서 위치 확인. 팀 개발환경 설치는 완료 | 장비 연결도, 소프트웨어 버전, 수동조작 기준선 기록 |
| 1. 구동·정지 기준선 | 수동 주행·정지, 명령 두절, 모드 전환, 속도·정지 측정 | 시험 절차와 로그/영상, 하드웨어 정지 수단 확인 |
| 2. Gazebo 모델·기본 구동 | 실물 치수·메카넘 휠·4개 구동축·센서 배치 모델, Gazebo 구동 설정, 수동 명령 연결 | 재현 가능한 모델·월드와 전후좌우 이동·회전·정지 시험. 실물과 시뮬레이션의 방향·속도 대응 기록 |
| 3. 경로·장애물 대응 | 경로 계획·재탐색, 사람 회피, 임시 장애물, 데드락 제한 | 장애물별 결과와 실패·복구 로그 |
| 4. 영상·대상 연결 | 카메라 입력, PPE 판정, 연속 관측, 추적 단절, 좌표 변환 | 분리된 평가자료, 성능과 좌표 오차 기록 |
| 5. 전달·복귀 통합 | 출동 조건, 전달 위치, 수령/미수령, 복귀, 오류 전이 | 요구사항 ID별 통합 실행 기록 |
| 6. 반복·인수 검증 | 통합 반복시험, 실패 원인, 시뮬레이션/실물 구분, 운용 문서 | 결과표, 운용 제한과 미해결 항목 |

이 순서는 요구명세서의 단계별 검증 흐름을 구조화한 제안입니다. 장비 준비와 팀 일정에 따라 조정하되 안전·인터페이스 확인을 통합 후반으로 미루지 않습니다.

## 7. 요구사항 추적과 시험 기록

각 요구사항 ID를 코드·설정·시험 시나리오·결과 증거와 연결합니다. 완료는 명세서의 완료 기준을 만족하는 증거를 검토한 뒤 갱신합니다.

시험 기록에는 요구사항 ID, 시나리오, 코드·환경 버전, 장비·지도·설정, 예상·실제 결과, 로그·영상 위치, 통과 여부와 실패 원인을 남깁니다. 시뮬레이션 통과를 실물 완료와 합치지 않습니다. 회의록의 접속·곡선 선회 기록만으로 개별 요구사항을 완료 처리하지 않습니다.

## 8. 주요 위험과 대응

| 위험 | 대응 방향 |
|---|---|
| 실제 하드웨어 사양·연결 미확정 | 장비 목록, 전원·통신·영상 출력·드라이버를 조사하고 미확인 상태를 기록 |
| 인터페이스 합의 전 병렬 구현 | 명령·상태·오류·좌표·시각 규칙을 먼저 문서화 |
| 안전 정지를 소프트웨어만으로 간주 | 로봇 측 독립 정지 수단을 확인하고 PC·네트워크 장애 시험 수행 |
| 위치나 대상 관측이 오래됨 | 유효시간을 검사하고 만료 시 접근·자동 복귀 제한 |
| 센서가 투명·반사체를 놓침 | 재질·각도·거리별 시험 전까지 지도상 제한구역으로 등록 |
| 사람을 장애물로 취급하지 않음 | PPE 상태와 무관하게 사람 회피를 시험 |
| 한 영역에 통합 업무 집중 | 공통 인터페이스 조기 합의, 기능별 시험 책임과 교차 검토 배정 |
| 예제가 검증된 기능으로 오인 | examples 자료와 제품 구현·인수시험 증거를 분리 |

### 미팅 전 기술 작업

1. Raspberry Pi의 OS·ROS 배포판과 examples/manual/manual_jiy.py의 실행 환경을 기록합니다.
2. 기존 Flask 명령(FORWARD/BACKWARD/LEFT/RIGHT/STOP)에서 하드웨어 출력 부분을 분리하고, Gazebo용 ROS 출력 경로를 설계합니다.
3. 라즈봇의 차체·휠 치수, 모터 배치, 센서·카메라 위치, 구동 보드 인터페이스를 확인해 메카넘 모델을 구성합니다.
4. Gazebo에서 기존 버튼 동작과 같은 전후·제자리 회전·정지를 검증하고, 명령 갱신이 끊겼을 때 정지 동작을 확인합니다.
5. 실물 수동조작과 Gazebo 시뮬레이션의 명령·속도 대응을 기록합니다.

안전 정지 기준과 1차 시연 범위에 의존하는 실물 주행은 미팅에서 원칙을 정한 뒤 진행합니다.
